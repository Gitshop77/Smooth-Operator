# Wave 1 — AUD-1 loop + prompts

Read-only audit of the agent decision loop (`src/lib/agent/loop/`, incl. `phases/`, `helpers/`, `context/`) and the prompt system (`src/lib/agent/prompts/`, `src/lib/agent/loop/messages*.ts`). Every finding was verified against source; the pinned suites `tests/observation-window-placeholder.test.ts`, `tests/loop-detector.test.ts`, and `tests/failed-llm-usage.test.ts` (29 tests) pass and do NOT cover these cases.

- [I] src/lib/agent/loop/messages-utils.ts:127 (also 60-71) — the stale-observation placeholder ships `r.action` ARGS unredacted and unescaped to the provider on every step. `redactHistoryForPrompt` (loop/messages.ts:145-216) redacts `message` / `extractedContent` / evaluation / memory / goal but leaves `r.action` untouched, and `actionArgsPlaceholder` renders every enumerable param (`text=`, `url=`, `code=`, `value=`, …) with no `redactBoth`, no `wrapUntrusted`, no `escapeXml`. A model-echoed credential in an action arg (e.g. a key-shaped token the task text contained, echoed into `navigate(url=…)` / `evaluate(code=…)`) round-trips to the provider on every subsequent step — the exact class of leak the other seams exist to prevent (cf. messages.ts:340-358 on substituted-secret round-trips; tools/handlers/input.ts:251-269 masks the substituted MESSAGE but not the action). The placeholder's own tests (observation-window-placeholder.test.ts:42) assert the args render but never their redaction. Fix: redact action args in `redactHistoryForPrompt` (or apply `redactKeyShapes` + escape in `actionArgsPlaceholder`).
- [M] src/lib/agent/loop/helpers/llm-calls.ts:386-394 — when a navigator retry attempt throws with NO `usage` (network/HTTP error), `lastUsage` is not cleared, so the `llm-call-end` error event reports the PREVIOUS attempt's tokens (attempt 1 success+parse-fail → attempt 2 provider error: attempt 1's tokens are reported twice in the event stream). The cost ledger is unaffected (usage only accrues with a real record), but per-attempt UI/analytics double-count. `tests/failed-llm-usage.test.ts` only covers failures WITH usage. Fix: clear `lastUsage` (or report `undefined`) when `getFailedCallUsage` returns undefined.
- [M] src/lib/agent/loop/context/injection-points.ts:130 — the oscillation nudge hardcodes `LoopDetector.oscillationWarningText(2, cycles)` while `shouldWarnOscillation` also detects period-3 cycles (loop/loop-detector.ts:15, 121-135); a period-3 stuck run is told "alternating between 2 distinct states". `tests/loop-detector.test.ts:156-167` asserts period-3 DETECTION but never the warning text. Fix: thread the detected period into the text.
- [M] src/lib/agent/loop/orchestrator-helpers.ts:1122-1124 — dead branch: every `classifyError` result with `category === "cancelled"` is rewritten to `"network"` at lines 1096-1105 before this check, so `classified.category === "cancelled"` is unreachable. If a future refactor removes the rewrite (or a new classifier emits "cancelled"), the branch would exit via `exitStoppedByUser` on mere provider wording — the exact false-cancellation the rewrite guards against. Delete the branch or move the rewrite into `classifyError`.
- [M] src/lib/agent/loop/helpers/judges.ts:32-42 — `consecutiveJudgeRejections` resets only in `finalize` or when the threshold trips, so rejections separated by many steps (e.g. steps 5, 45, 46) still trigger `judgeReplanForced` despite the "consecutive" contract (JUDGE_CONSECUTIVE_REJECT_LIMIT = 3). The forced re-plan is itself harmless, but the bound does not bound a stubborn judge+planner cycle over time as documented. Fix: reset the counter on any non-done step (or cap by step gap).
- [M] src/lib/agent/loop/phases/navigator.ts:29 (and 359-364) — `lastChallengeKey` is module-level and only cleared when a subsequent observation reports NO challenge; it survives across runs in the same service-worker lifetime, so a second run hitting the same challenge kind suppresses the human-readable "Anti-bot challenge detected" info line (the per-step dedupe leaks across runs). Fix: reset in a per-run init (alongside `clearRedactionMemo`).
- [M] src/lib/agent/loop/orchestrator-helpers.ts:838-840 — the `budget-warning` event fires at `step === floor(maxSteps * 0.75)` even when the matching prompt nudge is suppressed (injection-points.ts:41-56 returns null when the step is the last), so tiny-budget runs (maxSteps 2-4) emit a "75%" UI warning with zero steps remaining while the model never sees a budget nudge. Fix: reuse `injectBudgetWarning`'s is-last-step condition at the event site.

Note: no [C] findings. The loop's control flow, security posture, and budget accounting checked out end-to-end: the run-phase state machine is fail-closed with every real transition legal (recover edges, verify→observe, sticky terminal); no double-`done` emission (idempotent `finish` + `terminalEmitted`); step advancement is monotone with a machine-enforced no-progress guard in `runAgentLoop`; user-stop is keyed only on the root signal (provider "aborted" wording is correctly demoted to transient, except the dead branch above); cost-cap checks run at every accrual point incl. inside retries and compaction; the compaction budget is deterministic (bytes-reserved for system prompt + prior-block, `boundPromptTextV1`, plus the fail-closed profile assert at known contexts); history redaction covers both navigator and planner seams symmetrically with version-keyed caches invalidated on secret-set change (redaction-memo.ts + messages.ts item cache); key-shaped secrets are redacted in every outbound LLM sink (navigator, planner, compaction, judge — judges.ts:200) except the action-args channel above; `runPauseCheck`/`waitForTakeoverResume` never emit misleading resumed events (deadline/abort distinguished, latest-wins registry bounded at 10); the loop detector's warning-threshold logic is monotone (no 5/8/12 flicker); observation caps are derived from the effective context with a fail-closed budget assert at the llm-direct seam; `earlyStop` clamps degenerate thresholds and exempts legitimately-repeatable action types; config values are zod-validated (`.min(1)`) so degenerate intervals/maxFailures cannot fail-open.
