Findings are verified at the cited source lines and ordered by severity.

- [I] `llm-direct.ts:858,864` — `summarizeCallDirect` (wired as the production `summarizeCall` for compaction + judging) is the one direct-call path missing the reasoning-adaptation the navigator (`:733`) and planner (`:814`) both have: it sends `temperature: 0` unconditionally (HTTP 400 on OpenAI reasoning models — documented at `provider-config.ts:390-394`) and calls `requireDirectVisibleOutput` with NO `chatWithVisibleOutputRetry`. On thinking models (qwen3-thinking, LiquidAI LFM — the retry's own docstring `:567-574` says they burn the whole output window routinely) every compaction summarization and judge call throws `REASONING_ONLY_OUTPUT`; the compaction runner absorbs the failure and returns `null` (`compaction-runner.ts:259-281`), so compaction silently never runs, judge verdicts stay `unverified`, and context growth eventually trips the fail-closed budget assert on long tasks. Untested: `llm-direct-gating.test.ts` covers the retry for navigator/planner only.
- [I] `content-main.ts:17-18` + `content.ts:69-79` — the shadow-piercer and console capture install at `document_start` in the MAIN world on every page, and every admitted page console call is stringified and relayed via `chrome.runtime.sendMessage`, which wakes the service worker even when the console ring is disabled (the `consoleLogEnabled` gate is SW-side only, `rate-limit-tracker.ts:171-174`). Persistent SW-wake + per-call `JSON.stringify` cost on pages that have nothing to do with any run; the capture is also not gated by stealth mode.
- [M] `llm-direct.ts:670-671` — stale comment: "It defaults off because DOM + viewport AX are sufficient for most pages", but `getEnableScreenshots()` is `?? true` at `:227` and the options HTML/settings-sync agree it defaults ON.
- [M] `credential-service.ts:122-124` — `saveEnteredCredential` creates a NEW vault handle with `expectedRevision: 0` whenever the stored manifest's provider differs from the saved entry, but never deletes the previous provider's record — encrypted credential blobs orphan and accumulate across provider switches (same-provider re-saves reuse the handle and are fine).
- [M] `llm-direct.ts:586-599` — `chatWithVisibleOutputRetry` swallows the first (reasoning-only) attempt's error, discarding its attached token usage, so reasoning-model steps under-report up to `maxTokens` of tokens/cost to the loop's cost accounting on every retried step.
- [M] `provider-config.ts:466-469` vs `:486` — the unknown-provider fallback comment claims the agent "can still make LLM calls instead of being locked out", but the key is deliberately cleared at `:486`, so the fallback always throws `requireApiKey` and the agent IS locked out until reconfiguration (the exfiltration rationale at `:480-485` is correct — the comment contradicts the behavior).

No [C] findings in this layer. The security-critical boundaries reviewed (provider canonical-host/SSRF gate, provenance fail-safe, vault AES-GCM + revision checks, content-script token/admission/stale-element guards, storage-access gating) were all verified sound, and the `<screenshot>` marker plant surface is closed: `wrapUntrusted`/`sanitizeUntrusted` redacts prompt-tag blocks including `screenshot` (`security-injection.ts:52,92`) on every page-derived render path.
